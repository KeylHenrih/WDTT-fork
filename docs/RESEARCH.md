# Исследование существующих реализаций WDTT (Этап 0)

В данном документе приведён сравнительный архитектурный и технический анализ существующих реализаций туннеля «WireGuard поверх TURN/DTLS с маскировкой под медиатрафик звонка» на основе прямого изучения исходного кода эталонных репозиториев.

> [!NOTE]
> **Лицензионная формулировка:** Проект `wdtt-rs` разрабатывается как **независимая реализация по собственной спецификации** (`docs/PROTOCOL.md`) под лицензией **GPL-3.0**. Исходный код эталонных проектов (`PWDTT`, `csqtt`, `vk-turn-proxy`) читался исключительно для анализа проводных протоколов, структур данных и выявленных дефектов. Ни одной строки исходного кода из `csqtt` (PolyForm Noncommercial) **не заимствовано**.

## 2. Анализ каждого проекта

### 2.1 `cacggghp/vk-turn-proxy` (Go core)

#### Что реализовано
- Минимальный клиент и сервер на Go с использованием библиотек Pion (`pion/dtls/v3`, `pion/turn/v5`).
- Режимы работы: UDP (проксирование WireGuard) и VLESS (smux + KCP поверх DTLS для проксирования TCP/Xray).
- Авторизация в VK Звонках и Яндекс Телемосте для автоматического получения временных TURN-учётных данных.
- Поддержка параллельных DTLS-потоков (флаг `-n`, по умолчанию 10 для VK, 1 для Яндекса).

#### Проводной протокол (Wire Protocol)
- **Транспорт:** DTLS 1.2 поверх UDP или TCP соединения с TURN-сервером через STUN ChannelData (`0x4000..0x7FFF`).
- **DTLS параметры:** `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`, самоподписанный ECDSA-сертификат, сгенерированный на лету (`selfsign.GenerateSelfSigned`), Extended Master Secret обязателен, Connection ID (CID) 8 байт.
- **Полезная нагрузка:** В режиме WireGuard сырые UDP-пакеты WireGuard передаются непосредственно как DTLS Application Data без дополнительной инкапсуляции.

#### Получение TURN-учётных данных (VK API цепочка)
1. **Токен 1 (Анонимный доступ):** POST `https://login.vk.ru/?act=get_anonym_token`
   - Параметры: `client_id`, `client_secret`, `token_type=messages`, `version=1`, `app_id`.
   - Ответ: JSON с `data.access_token` (`token1`).
2. **Предпросмотр звонка:** POST `https://api.vk.ru/method/calls.getCallPreview?v=5.275&client_id=...`
   - Параметры: `vk_join_link=https://vk.com/call/join/<hash>`, `access_token=token1`.
3. **Токен 2 (Анонимный токен звонка):** POST `https://api.vk.ru/method/calls.getAnonymousToken?v=5.275&client_id=...`
   - Параметры: `vk_join_link`, `name` (псевдослучайное имя), `access_token=token1`.
   - Ответ: `response.token` (`token2`) либо объект ошибки капчи `error`.
4. **Токен 3 (Сессионный ключ OK CDN):** POST `https://calls.okcdn.ru/fb.do`
   - Параметры: `method=auth.anonymLogin`, `session_data={"version":2,"device_id":"<uuid>","client_version":1.1,"client_type":"SDK_JS"}`, `application_key=CGMMEJLGDIHBABABA`.
   - Ответ: `session_key` (`token3`).
5. **Токен 4 (TURN сервер):** POST `https://calls.okcdn.ru/fb.do`
   - Параметры: `method=vchat.joinConversationByLink`, `joinLink=<hash>`, `anonymToken=token2`, `session_key=token3`, `isVideo=false`, `protocolVersion=5`, `capabilities=2F7F`.
   - Ответ: JSON с объектом `turn_server`:
     - `username`: строка авторизации TURN (например, `<call_id>:<user_id>`).
     - `credential`: пароль TURN.
     - `urls`: список адресов вида `turns:turn-msk-xxx.okcdn.ru:443?transport=tcp` или UDP.

#### Потоки и балансировка (Поведение)
- Все N параллельных DTLS-воркеров вычитывают дейтаграммы из одного общего буферизированного канала Go емкостью 2000 элементов.
- **Особенность диспетчеризации:** Пакеты WireGuard считываются из сокета и передаются в общий канал, откуда воркеры забирают их в порядке планировщика среды исполнения. Это приводит к изменению порядка следования пакетов (out-of-order delivery). В результате TCP внутри WireGuard генерирует Duplicate ACK и снижает размер окна перегрузки (congestion window).
- На стороне сервера: каждый DTLS-поток открывает отдельный UDP-сокет к WireGuard. WireGuard определяет адрес пира по последнему полученному пакету, из-за чего возвратный трафик направляется только в один из открытых DTLS-потоков.

#### Обработка капчи
- Автоматическая: парсинг Proof-of-Work (PoW) и попытка решения слайдер-капчи по градиентам изображения.
- Ручная (`manual_captcha`): запуск локального HTTP reverse-proxy на `127.0.0.1:8765`, открытие системного браузера на перехваченном URL капчи, перехват результирующего `success_token`.

### 2.2 `luminescq/PWDTT` (Go + Wails)

#### Что реализовано
- Кроссплатформенный клиент для Windows, Linux и macOS на базе фреймворка Wails v2 (Go бэкенд + веб-интерфейс на React / Vite).
- Формат ссылок: поддержка устаревшего `wdtt://` и нового `qwdtt://config?...`.
- Дополнительный уровень обфускации трафика: **RTP-obfs (ChaCha20-Poly1305)** поверх DTLS.
- Автоматический запрос конфигурации WireGuard с сервера (`GETCONF`).

#### Формат ссылок (URL)
1. **Legacy `wdtt://`:**
   `wdtt://<IP>:<DTLS_PORT>:<WG_PORT>:<PROXY_PORT>:<PASSWORD>[:<HASH1>,<HASH2>,...][#<NAME>]`
   - Пример: `wdtt://198.51.100.1:56000:56001:0:SecretPass:hash1,hash2#HomeServer`
2. **Modern `qwdtt://config?`:**
   `qwdtt://config?peer=<IP>:<PORT>&pass=<PASSWORD>&hashes=<H1>,<H2>&workers=<N>&port=<LOCAL_PORT>&name=<NAME>`
   - Диапазон workers: 9–108 (до 4 хешей по 27 воркеров).

#### RTP-obfs и криптография
- Пакеты WireGuard маскируются под RTP v2 медиапоток (RFC 3550).
- **Заголовок RTP (12 байт):**
  - Байт 0: `0x80 | 0x20` (V=2, P=1 — флаг наличия padding).
  - Байт 1: `PayloadType` (111 — Opus audio, 96 — video).
  - Байты 2–3: `Sequence Number` (uint16, big-endian).
  - Байты 4–7: `Timestamp` (uint32, big-endian, инкремент 960 на пакет в аудио).
  - Байты 8–11: `SSRC` (uint32, псевдослучайный идентификатор источника).
- **Шифрование полезной нагрузки:** ChaCha20-Poly1305 (IETF, 12-байтный nonce).
  - Вывод ключа: HKDF-SHA256:
    - Secret: пароль сервера (`password`).
    - Salt: `b"WDTT-WRAP-v1"`.
    - Info: `b"rtp-obfs/chacha20poly1305"`.
    - Key Length: 32 байта.
  - Nonce (12 байт): `SSRC (4 байта) || seq (2 байта) || 0x00 0x00 (2 байта) || Timestamp (4 байта)`.
  - AAD: первые 12 байт RTP-заголовка.
  - Padding: в конец пакета дописывается случайный паддинг (1–24 байта для аудио, 1–60 байт для видео), последний байт содержит общую длину паддинга `padTotal`.

#### Управление сетевыми интерфейсами и маршрутами
- **Linux:** настройка маршрутизации и виртуальных интерфейсов выполняется через внешние вызовы утилит `ip` и `wg` с повышенными привилегиями.
- **Windows:** динамически использует библиотеку `wintun.dll`, настраивает интерфейс через системные утилиты netsh/route.
- **Потребление ресурсов `[Архитектурная оценка]`:** фреймворк Wails запускает процесс веб-представления (WebView2 / WebKit). В результате процесс GUI по типовым оценкам фреймворка потребляет порядка 180–260 МБ RSS в простое при открытом окне.

### 2.3 `amurcanov/csqtt` (Android + Rust, PolyForm NC)

#### Архитектурные особенности
- Архитектура с разделением на нативный клиент (статическая библиотека Rust под Android), сервер и разделяемые структуры данных.
- Реализация протокола на Rust с использованием криптографических примитивов AES-GCM.
- Поддержка расширения DTLS-SRTP для согласования ключей защиты медиаданных.
- **Схема фрагментации пакетов:**
  - Служебный заголовок фрагмента (8 байт): идентификатор протокола, индекс фрагмента, общее число фрагментов, идентификатор пакета, общая длина дейтаграммы.
  - Буфер сборщика фрагментов на 512 слотов с таймаутом ожидания недостающих частей 300 мс.
- **Взаимодействие с Android:**
  - Приём файлового дескриптора виртуального сетевого интерфейса в нативный код через локальный сокет домена Unix.
  - Фоновое удержание системных блокировок сна процессора и режима высокой производительности Wi-Fi на время активности туннеля.

### 2.4 `SpaceNeuroX/proxy-turn-vk-android` (qWDTT) и `Ivan4537/WDTT-Plus`

#### Особенности форков и ограничения VK TURN
- **Агрегация ссылок звонков:** клиент разделяет общий пул воркеров по хешам (например, 4 хеша по 18 воркеров = 72 потока).
- **Квоты аллокаций TURN `[Измерено по коду]`:**
  - Серверы TURN возвращают STUN Error 486 (Allocation Quota Reached), если превышается допустимое число одновременных релейных портов на один токен, либо при параллельном запуске нескольких запросов Allocate без интервала.
  - В форках для сглаживания запросов используется стаггеринг (интервал 200–500 мс между запросами) и ограничение до 9 воркеров на группу.
  - **Вывод для `wdtt-rs`:** Лимит пула на один хеш звонка должен составлять **не более 8 потоков** со ступенчатым стартом (задержка $\ge 250$ мс между вызовами Allocate).
- **Режим Direct / Raw-IP:** передача IP-пакетов без WireGuard (RTP-obfs инкапсулирует IP-пакеты напрямую в TUN-интерфейс сервера с NAT).
- **Характеристики работы со структурами данных `[Измерено по коду]`:**
  - В некоторых реализациях проверка replay-окна выполняется через хеш-таблицы с блокировкой мьютекса на каждую дейтаграмму, что создаёт дополнительные задержки и накладные расходы памяти.

### 2.5 `anton48/vk-turn-proxy-ios`

#### Ключевой инсайт: Anti-Replay окно WireGuard
В репозитории `vk-turn-proxy-ios` (в инструменте `tools/turn_srtp_server`) зафиксировано:
- В ядре WireGuard для каждой Security Association действует **одно** скользящее окно защиты от повторов (anti-replay window, RFC 6479) размером 8128 пакетов (`127 * 64`).
- Если один сеанс WireGuard полосатится (striping) по N независимым путям TURN без сохранения попоточного порядка, пакеты по более медленным путям отстают от счетчика быстрых путей.
- При пропускной способности 1 Гбит/с ($\sim 104{,}000$ pps) задержка 100 мс между путями даёт отставание $10{,}400$ пакетов.
- Если отставание превышает 8128 пакетов, WireGuard **молча отбрасывает пакеты на стороне приёма** (silent packet discard).
- **Вывод для wdtt-rs:** Необходимы **Active Skew Limiter** в планировщике (ограничение джиттера путей до 35 мс) и **WG-Counter Resequencer** на стороне клиента.

## 3. Сводная матрица накладных расходов и MTU

| Уровень / Заголовок | Размер (байт) | Статус / Примечание |
|---|---|---|
| Внутренний IP-пакет (WireGuard payload) | $MTU_{inner}$ | Целевой MTU туннеля (TCP MSS = $MTU_{inner} - 40$) |
| WireGuard Data Header | 32 | `[Измерено по коду]` Type (4) + Receiver Index (4) + Counter (8) + Tag (16) |
| RTP Header | 12 | `[Измерено по коду]` V=2, P=1, PT, Seq, Timestamp, SSRC |
| AEAD Tag (RTP-obfs) | 16 | Poly1305 или AES-GCM tag |
| Random Padding | 0..4 (min) / 1..24 (audio) | `[Архитектурная оценка]` По умолчанию минимальный (0..4 Б) |
| DTLS 1.2 Record Header | 13 | ContentType (1) + Version (2) + Epoch (2) + Seq (6) + Length (2) |
| DTLS Record IV + AEAD Tag | 16..24 | Явный nonce / auth tag DTLS |
| STUN ChannelData Header | 4 | Channel Number (2) + Length (2) |
| Внешний UDP Header | 8 | Порты, длина, контрольная сумма |
| Внешний IPv4 Header | 20 | Без опций |
| **Итого накладные расходы** | **122 .. 189 байт** | `[Архитектурная оценка]` Зависит от режима padding и наличия DTLS |

### Расчёт оптимального MTU:
- При внешнем MTU 1500: $MTU_{inner} \le 1500 - 189 = 1311$ байт (рекомендуется **1200** байт).
- При сотовом внешнем MTU 1280: $MTU_{inner} \le 1280 - 189 = 1091$ байт (рекомендуется **1080** байт).

## 4. Сводка архитектурных различий и оптимизаций

1. **Сохранение попоточного порядка пакетов (Flow Preservation):**
   Распределение дейтаграмм без сохранения порядка по параллельным путям нарушает работу механизмов TCP congestion control и anti-replay окна WireGuard. В `wdtt-rs` применяется Flow Hashing (ADR-0002) и WgResequencer (ADR-0006).
2. **Устранение динамических аллокаций в горячем пути ввода-вывода:**
   Использование предвыделенных пулов буферов (slab allocators) и исключение аллокаций динамических коллекций при проверке nonces.
3. **Разделение привилегий на десктопе:**
   Использование легковесного системного демона (`wdttd`) с разделением прав доступа и коммуникацией через локальный IPC, исключающее выполнение неконтролируемых внешних команд.
4. **Легковесный графический интерфейс:**
   Отказ от встроенного браузерного движка (Wails/Electron) в пользу нативного рендеринга на Slint, снижающий потребление памяти на порядок.
5. **Энергосбережение на мобильных устройствах:**
   Отказ от постоянного удержания блокировок сна и согласование работы с жизненным циклом Android Doze.
6. **Прямая интеграция с интерфейсом TUN:**
   Передача дескриптора TUN непосредственно в ядро Rust без промежуточных сокетных прокси.
