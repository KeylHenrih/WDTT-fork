## 1. Цель и принципы измерений

Согласно Разделу 9 технического задания, **любое утверждение о производительности должно подтверждаться измерением**.
Нельзя заявлять «быстрее» или «легче» без воспроизводимых цифр, профилирования и точного описания стенда.

Цели данного документа:
1. Зафиксировать единую методику измерений для baseline-проектов (PWDTT, qWDTT/WDTT-Plus, CSQTT) и будущего `wdtt-rs`.
2. Описать конфигурацию эталонного испытательного стенда (Controlled Lab и Real World `root@cz-1`).
3. Сформировать матрицу целевых метрик и критериев приемки (Acceptance Gates) с чётким разделением того, что измерено в коде, а что является предварительной архитектурной оценкой.

## 2. Архитектура испытательного стенда (Test Bench)

Для исключения внешних сетевых флуктуаций измерения разделяются на два уровня:

### 2.1 Стенд Controlled Lab (Локальная сеть / veth / loopback + `tc netem`)
- Полный контроль задержки, джиттера и потерь пакетов через Linux Traffic Control:
  ```bash
  # Пример симуляции асимметрии каналов (Path 1 vs Path 2):
  tc qdisc add dev veth1 root netem delay 10ms 2ms
  tc qdisc add dev veth2 root netem delay 110ms 5ms
  ```
- Изолированные ядра CPU (`taskset` / `cgroups`).
- Исключение влияния загрузки внешних TURN-серверов VK для получения чистых цифр производительности ядра (crypto, buffer pool, framing).

### 2.2 Стенд Real World (`root@cz-1` + VK TURN + LTE/Wi-Fi)
Для снятия baseline PWDTT и WDTT-Plus и проверки сквозного туннеля используется тестовый VPS `root@cz-1` со строгим соблюдением правил:
1. **Изоляция:** Действующий сервер WDTT Plus **не останавливается и не модифицируется**; перед любыми действиями сохраняются резервные копии конфигов.
2. **Отдельные порты:** Сервер `wdtt-rs` запускается на выделенных, не конфликтующих портах (например, DTLS `57000`, WG `57001`).
3. **Отдельный пользователь:** Сервис развертывается под непривилегированным пользователем `wdtt-test` (root используется исключительно для разового создания интерфейса/пользователя).
4. **Сетевая безопасность:** Любые команды, потенциально затрагивающие фаервол, правила маршрутизации или SSH-доступ, предварительно согласовываются с пользователем.
5. **Щадящий режим нагрузки:** Нагрузочные тесты через VK короткие и умеренные, во избежание блокировки пользовательских хешей звонков и исчерпания трафика VPS.
6. **Конфиденциальность:** Пароли, приватные ключи и хеши ссылок **никогда не сохраняются в репозитории и не пишутся в логи**.
7. **Baseline-ссылка:** Измерения PWDTT и WDTT-Plus снимаются против уже развёрнутого на `cz-1` сервера по рабочей ссылке пользователя (запрашивается у пользователя перед тестом).

## 3. Программа измерений и метрики

### 3.1 Пропускная способность (Throughput)
- Инструмент: `iperf3 -c <server_ip> -t 30`
- Тестовые сценарии:
  1. **TCP Single Stream (`iperf3 -P 1`):** Сравнение режима чистого Flow-Hash против режима Packet Spraying с клиентским ресеквенсером. Проверка отсутствия искусственного ограничения скорости одного соединения емкостью одного потока.
  2. **TCP Multi Stream (`iperf3 -P 8`):** Агрегированная пропускная способность при насыщении всех путей.
  3. **UDP 100 Mbps / 500 Mbps / 1 Gbps (`iperf3 -u -b <rate>`):** Измерение потерь (Packet Loss %) и джиттера (Jitter ms).
  4. **Направление:** Uplink (клиент -> сервер) и Downlink (сервер -> клиент).

### 3.2 Задержка и RTT под нагрузкой (Bufferbloat)
- Измерение RTT в покое: 100 ICMP эхо-запросов с интервалом 200 мс (`ping -c 100 -i 0.2 <tunnel_ip>`).
- Измерение RTT под нагрузкой (Loaded Latency): запуск непрерывного пинга параллельно с `iperf3` насыщающим канал.
- Bufferbloat: $\Delta RTT = RTT_{\text{loaded}} - RTT_{\text{idle}}$.

### 3.3 Anti-Replay Skew тест (`tests/netem_replay_skew.sh`)
- На стенде Controlled Lab поднимаются два veth-интерфейса:
  - Path 1: `delay 10ms`
  - Path 2: `delay 110ms` (разница задержек 100 мс).
- Запускается трафик 1 Гбит/с (`iperf3`).
- **Критерий успешности:** 0 отброшенных пакетов по счетчику `replay drops` WireGuard (`wg show <iface> dump` / метрики boringtun).

### 3.4 Процессор (CPU Efficiency)
- Инструменты: `perf stat -d`, `perf top`, генерация FlameGraph (`flamegraph.pl`).
- Метрики:
  - Instructions per Cycle (IPC) в горячем цикле datapath.
  - CPU Cycles per Byte (такты CPU на переданный байт данных).
  - Нагрузка на сервер при $N = 10, 50, 200$ активных клиентов.

### 3.5 Память и утечки (Memory RSS)
- Инструменты: `valgrind --tool=massif`, `/proc/<pid>/smaps_rollup`, `heaptrack`.
- Метрики:
  - RSS демона (`wdttd`) в покое и при передаче 1 Гбит/с трафика.
  - RSS GUI-клиента при открытом активном окне и в свёрнутом в трей состоянии.
  - 24-часовой Soak Test: контроль отсутствия линейного дрейфа памяти ($< 1$ МБ за 24 ч).

### 3.6 Энергопотребление и Doze на Android
- Инструменты: `dumpsys batterystats --charged`, Battery Historian, Perfetto.
- Тестовые сценарии:
  - Сценарий A: Экран выключен, устройство в покое 1 час. Контроль входа в Deep Sleep / Doze при полном отсутствии постоянных `WakeLock`.
  - Проверка снятия постоянного WakeLock на нескольких устройствах различных вендоров (AOSP/Pixel, Xiaomi/MIUI, Samsung/OneUI) для верификации поведения планировщиков Doze.
  - Сценарий B: Экран включен, интерфейс открыт (частота обновления UI строго $\le 1$ Гц).
  - Сценарий C: Активная фоновая передача трафика через туннель.
