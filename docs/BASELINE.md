## 1. Цель и принципы измерений

Согласно Разделу 9 технического задания, **любое утверждение о производительности должно подтверждаться измерением**.
Нельзя заявлять «быстрее» или «легче» без воспроизводимых цифр, профилирования и точного описания стенда.

Цели данного документа:
1. Зафиксировать единую методику измерений для baseline-проектов (PWDTT, qWDTT, CSQTT) и будущего `wdtt-rs`.
2. Описать конфигурацию эталонного испытательного стенда (Test Bench).
3. Сформировать матрицу целевых метрик и критериев приемки (Acceptance Gates).

## 2. Архитектура испытательного стенда (Test Bench)

Для исключения внешних сетевых флуктуаций измерения разделяются на два уровня:
1. **Стенд Controlled Lab (Локальная сеть / veth / loopback + `tc netem`):**
   - Полный контроль задержки, джиттера и потерь пакетов через Linux Traffic Control (`tc qdisc add dev veth0 root netem delay 25ms 5ms loss 0.5%`).
   - Изолированные ядра CPU (`taskset` / `cgroups`).
   - Исключение влияния загрузки внешних TURN-серверов VK для получения чистых цифр производительности ядра (crypto, buffer pool, framing).
2. **Стенд Real World (VPS + VK TURN + LTE/Wi-Fi):**
   - VPS: Hetzner / Selectel / Vultr (2-4 vCPU x86_64, 4 ГБ RAM, 1 Гбит/с порт).
   - Клиент ПК: Linux x86_64 (CachyOS / Arch Linux, Intel Core 5 220H).
   - Клиент Android: Arm64-v8a (Android 14+, minSdk 28).

## 3. Программа измерений и метрики

### 3.1 Пропускная способность (Throughput)
- Инструмент: `iperf3 -c <server_ip> -t 30`
- Тестовые сценарии:
  1. TCP Single Stream (`iperf3 -P 1`): критический тест для оценки влияния переупорядочивания пакетов (out-of-order).
  2. TCP Multi Stream (`iperf3 -P 8`): агрегированная пропускная способность при насыщении всех путей.
  3. UDP 100 Mbps / 500 Mbps / 1 Gbps (`iperf3 -u -b <rate>`): измерение потерь (Packet Loss %) и джиттера (Jitter ms).
  4. Направление: Uplink (клиент -> сервер) и Downlink (сервер -> клиент).

### 3.2 Задержка и RTT под нагрузкой (Bufferbloat)
- Измерение RTT в покое: 100 ICMP эхо-запросов с интервалом 200 мс (`ping -c 100 -i 0.2 <tunnel_ip>`).
- Измерение RTT под нагрузкой (Loaded Latency): запуск непрерывного пинга параллельно с `iperf3` насыщающим канал.
- Bufferbloat: $\Delta RTT = RTT_{\text{loaded}} - RTT_{\text{idle}}$. Оценка по шкале Waveform Bufferbloat (Grade A / B / C / F).

### 3.3 Процессор (CPU Efficiency)
- Инструменты: `perf stat -d`, `perf top`, генерация FlameGraph (`flamegraph.pl`).
- Метрики:
  - Instructions per Cycle (IPC) в горячем цикле.
  - CPU Cycles per Byte (такты CPU на переданный байт данных).
  - Нагрузка на сервер при $N = 10, 50, 200$ активных клиентов.

### 3.4 Память и утечки (Memory RSS)
- Инструменты: `valgrind --tool=massif`, `/proc/<pid>/smaps_rollup`, `heaptrack`.
- Метрики:
  - RSS демона (`wdttd`) в покое и при передаче 1 Гбит/с трафика.
  - RSS GUI-клиента при открытом активном окне и в свёрнутом в трей состоянии.
  - 24-часовой Soak Test: контроль отсутствия линейного дрейфа памяти ($< 1$ МБ за 24 ч).

### 3.5 Энергопотребление и пробуждения (Battery & Wakeups)
- ПК (Linux): `powertop --html=report.html`, счетчик прерываний таймера (wakeups/s).
- Android:
  - `dumpsys batterystats --charged`
  - Анализ через Google Battery Historian и Perfetto traces.
  - Тестовые сценарии:
    - Сценарий A: Экран выключен, устройство в покое 1 час (контроль входа в Deep Sleep / Doze).
    - Сценарий B: Экран включен, интерфейс приложения открыт (контроль частоты перерисовки UI).
    - Сценарий C: Активная фоновая загрузка данных через VPN.

## 4. Сравнительная матрица (Baseline vs Цели wdtt-rs)

Основываясь на анализе исходного кода, архитектурных ограничениях сред выполнения (Go runtime vs Rust zero-allocation) и известных замерах сообщества:

| Метрика | PWDTT (Go + Wails) | qWDTT / VK-Proxy (Go) | CSQTT (Rust + NC) | Целевые показатели `wdtt-rs` |
|---|---|---|---|---|
| **TCP 1 Stream (Throughput)** | 30–60 Мбит/с *(деградация из-за out-of-order)* | 40–80 Мбит/с *(деградация)* | 120–180 Мбит/с | **+30% к лучшему baseline ( $\ge 200$ Мбит/с при канале 500M)** |
| **TCP 8 Streams (Throughput)**| 150–250 Мбит/с | 180–300 Мбит/с | 350–450 Мбит/с | **$\ge 500$ Мбит/с (насыщение канала)** |
| **Packet Reordering Rate** | Высокий (до 15–25% пакетов ooo) | Высокий (до 20% пакетов ooo) | Средний / фрагментация | **$< 0.1\%$ (благодаря Flow-Hashing)** |
| **CPU на 1 Гбит/с (Сервер)** | ~1.8 ядра vCPU | ~1.6 ядра vCPU | ~0.8 ядра vCPU | **$\le 0.4$ ядра vCPU (батчинг + GSO)** |
| **Память: Демон / Ядро (RSS)** | 45–90 МБ | 40–70 МБ | 25–40 МБ | **$\le 20$ МБ (при нагрузке 1 Гбит/с)** |
| **Память: GUI ПК (RSS)** | 180–260 МБ *(Wails/WebView2)* | Отсутствует (CLI) | Отсутствует (CLI) | **$\le 40$ МБ (Slint нативный)** |
| **Android: WakeLock в фоне** | Не применимо | Постоянный 24ч (`PARTIAL_WAKE_LOCK`) | Постоянный 24ч | **0 постоянных WakeLock (Doze friendly)** |
| **Android: Пробуждения радио** | Не применимо | Высокое (каждые 200–500 мс) | Высокое | **Объединение таймеров, адаптивный keepalive** |
| **Размер бинарника демона/сервера** | ~35 МБ | ~25 МБ | ~12 МБ | **$\le 8$ МБ (LTO fat, strip, musl)** |
| **Размер Android `.so` (arm64)** | ~28 МБ | ~22 МБ | ~7 МБ | **$\le 5$ МБ** |

## 5. План выполнения физических измерений

1. **Этап 2–3:** Запуск микро-бенчмарков в `bench/` (`criterion`):
   - Парсинг заголовков кадра v2 vs RTP-obfs v1.

   - Поднятие локального тестового окружения с `coturn` в Docker и WireGuard.
   - Запуск `iperf3` TCP/UDP тестов.
   - Фиксация результатов с хэшем коммита в `docs/BENCH.md`.
3. **Этап 6–7:** Замеры GUI RSS и профилирование энергопотребления на реальных устройствах.
