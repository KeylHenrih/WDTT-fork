## 1. Инфраструктура VK Звонков и стабильность TURN-сессий

### Вопрос 1.1: Срок жизни TURN-аллокации (Lifetime) и поведение при Re-allocation
- **Контекст:** В RFC 5766 стандартное время жизни аллокации TURN составляет 600 секунд (10 минут). По истечении этого времени клиент должен отправлять `Refresh` запрос с тем же `LIFETIME`. В коде `vk-turn-proxy` наблюдались случаи, когда серверы VK сбрасывали сессию через 5–15 минут независимо от Refresh, требуя повторного прохождения цепочки получения токенов (Re-allocation).
- **Вопрос к стенду/пользователю:** Требуется ли в `provider/vk` реализовать превентивное создание параллельной аллокации за 60 секунд до истечения старой (seamless handover) или достаточно стандартного `Refresh` с аварийным переподключением при получении 437/438 STUN ошибки?
- **Предложение:** Реализовать превентивный Refresh по таймеру ($0.8 \times \text{lifetime}$). Если Refresh отвергнут сервером — плавно поднять новый поток через цепочку API и переключить Flow-hash на него без сброса всей сессии.

### Вопрос 1.2: Лимиты на количество параллельных потоков с одного IP в VK
- **Контекст:** В оригинальном `vk-turn-proxy` использовалось 10 потоков, в `qwdtt` с 4 хешами пользователи выставляли до 72–108 потоков. Однако при частых запросах VK API возвращает `error_code: 29` (Rate Limit) или активирует слайдер-капчу.
- **Вопрос к пользователю:** Каков допустимый лимит одновременных TURN-аллокаций по вашему опыту использования сервиса? Стоит ли ограничить адаптивный пул сверху значением 8 потоков на сессию?
- **Рекомендация:** Ограничить $N_{\text{max}} = 8$ для одного хеша и $N_{\text{max}} = 16$ при мульти-хешинге.

## 2. Капча VK и взаимодействие с пользователем

### Вопрос 2.1: Политика при запросе сложной капчи (Honeypot / Slider)
- **Контекст:** VK периодически меняет типы проверок роботов: текстовая капча, PoW (proof-of-work в JS), сдвиг пазла (slider) и переход на веб-страницу `id.vk.com`.
- **Архитектурное решение в `wdtt-rs`:**
  Ядро `crates/core` и `crates/provider` полностью отделены от UI. Если провайдер сталкивается с капчей, он генерирует событие:
  `ProviderEvent::NeedsUserInteraction(InteractionChallenge::Captcha { url, session_token })`.
  - На Android: открытие системного WebView или Custom Tabs для решения.
  - На ПК: уведомление в графическом интерфейсе с кнопкой «Решить капчу в браузере» через локальный одноразовый callback или встроенное окно.
- **Вопрос к пользователю:** Утверждаете ли вы данное разделение обязанностей (ядро не знает про браузеры, взаимодействие инициируется через интерфейс провайдера)?

## 3. Выбор userspace WireGuard реализации (boringtun vs alternatives)

### Вопрос 3.1: Лицензия и модель интеграции boringtun
- **Контекст:** `boringtun` (Cloudflare) распространяется под лицензией BSD-3-Clause (полностью совместима с GPL-3.0), написан на Rust, проверен в высоконагруженных окружениях (Cloudflare WARP). Другие кандидаты: `wireguard-rs` (экспериментальный статус), ручная инкапсуляция через собственный протокольный парсер.
- **Решение:** Мы фиксируем выбор `boringtun` для userspace-режима (см. `docs/adr/0003-userspace-wireguard-boringtun.md`), но приоритетным на сервере Linux остаётся Linux Kernel WireGuard через локальный UDP сокет для максимальной производительности (zero-copy в ядре).

## 4. Требования к испытательному стенду (для прохождения Gate Этапа 3)

Для снятия физических baseline-показателей и проверки сквозного туннеля (Этап 3) потребуется:
1. **Тестовый сервер (VPS):** Доступ по SSH к VPS с публичным IP (желательно Linux x86_64, Ubuntu 24.04 или Debian 12) для развертывания сервера `wdtt-server` и `iperf3`.
2. **Рабочая ссылка VK Calls:** Ссылка вида `https://vk.com/call/join/<hash>` (бессрочный звонок без участников) для тестирования провайдера VK.
3. **Локальный стенд:** Поддержка Docker для автоматических тестов с `coturn` в CI.

*Примечание: До момента предоставления VPS все функциональные, юнит, property и фаззинг-тесты выполняются локально на виртуальном интерфейсе / veth / coturn.*

## 5. Ограничение блокировки по доменным категориям (`geosite:category-ads-all`)

**Ограничение:** блокировка по доменным категориям (`geosite:*`, в частности
`category-ads-all`) на уровне nftables **невозможна**. nft оперирует адресами
и портами пакета, а доменное имя в открытом виде на этом слое отсутствует —
оно появляется только после DNS-резолвинга. Правило `block` по доменной
категории не даёт packet-layer адресов.

**Следствие и принятое поведение:** трафик, для которого нет адресов
(рекламные и прочие доменные категории), **не блокируется вслепую** — он
уходит в туннель по общему правилу инверсии. Это сознательный выбор: слепая
блокировка по неполному набору адресов ломала бы легитимный трафик, а полный
набор адресов рекламных сетей недостижим без резолвинга.

**Что не входит в текущую задачу:** DNS-уровневая блокировка (отбрасывание
или подмена ответа по доменному имени в резолвере) — отдельная задача,
требующая хука в `crates/tun/src/dns/`. Не реализуется сейчас.
