## 1. Стендовая конфигурация и методика измерений

### 1.1 Стек и топология туннеля
```
[iperf3 client] (10.77.77.2)
       │
  (wg-client в netns wdtt-client-ns: ядро WireGuard, MTU 1200)
       │ UDP :51821 (SO_RCVBUF / SO_SNDBUF = 4 MB)
  (wdttd: клиентский демон, WDTT v2 Frame DATA, ChannelData 0x4000)
       │ veth: 192.168.100.2 -> 192.168.100.1
  (coturn TURN relay: 127.0.0.1:34780, ChannelData relay)
       │ UDP relayed port
  (wdtt-server: серверный демон, decapsulation, Pre-Auth Knock validation)
       │ UDP :51820 (SO_RCVBUF / SO_SNDBUF = 4 MB)
  (wg-server на хосте: ядро WireGuard, MTU 1200)
       │
[iperf3 server] (10.77.77.1)
```

### 1.2 Параметры безопасности и протокола
- **Pre-Auth Knock:** ChaCha20-Poly1305 со случайным nonce (12 байт), временным штампом, 16-байтным client_nonce, 16-байтным session_id и криптографическим рандомизированным padding (32 байта).
- **Anti-Replay Cache:** TTL-кеш использованных nonces (`max_skew_sec = 60с`).
- **Resequencer:** `WgResequencer` с адаптивным таймаутом gap (`1.25 * skew + 5ms`), изоляцией потоков по `receiver_index` и bypass для WireGuard пакетов Handshake (Types 1..3).
- **Silent Discard:** Все неаутентифицированные пакеты отбрасываются сервером без ответа (0 байт).
- **Dynamic Keepalives:** Таймеры обновления (Refresh Allocation, Permission, ChannelBind) рассчитываются динамически из значения `LIFETIME` ответа сервера (75% от полученного TTL).
- **Session Tracking & Port Reuse:** Сервер привязывает сессию к адресу/порту релея и session_id, отслеживая TTL активности; при повторном knock от клиента (смена порта/роуминг) выполняется безопасная перепривязка пира.

### 2.4 Системные и профилировочные метрики (на нагрузке 1 TCP-потока)

> [!IMPORTANT]
> **Утилизация CPU:** Однопоточный движок `wdtt-server` при скорости ~1.14–1.26 Гбит/с потребляет **99.88% мощности одного ядра CPU** (полное насыщение одного ядра). Приведённые ранее 3.6% являлись нормализацией по всем 16 vCPU хоста (`9.84s / (16 * 10s)`), что некорректно маскировало насыщение рабочего потока.

#### Формулы расчёта:
1. **Загрузка одного ядра (Single Core %):**
   $$\text{Core \%} = \frac{\Delta t_{\text{utime}} + \Delta t_{\text{stime}}}{\Delta t_{\text{wall}}} \times 100\% = \frac{9.84\,\text{с}}{10.05\,\text{с}} \times 100\% = 97.91\% \approx 100\% \text{ одного ядра}$$
2. **Интенсивность пакетов (PPS):**
   $$\text{PPS} = \frac{\text{Throughput (bits/sec)}}{\text{MTU} \times 8} = \frac{753.20 \times 10^6}{1200 \times 8} = 78\,458\text{ pps (при 753 Мбит/с)}$$
   $$\text{PPS при 1.26 Гбит/с} = \frac{1258.68 \times 10^6}{1200 \times 8} = 131\,112\text{ pps}$$
3. **Энергоэффективность (CPU-sec / Gbit):**
   - Передано данных за 10 с: $753.20\,\text{Мбит/с} \times 10\,\text{с} = 7.532\,\text{Гбит}$.
   - Сервер CPU ($9.84\,\text{с}$): $9.84 / 7.532 = \mathbf{1.306\,\text{CPU-с / Гбит}}$.
   - Клиент `wdttd` CPU ($6.29\,\text{с}$): $6.29 / 7.532 = \mathbf{0.835\,\text{CPU-с / Гбит}}$.
   - Суммарно (сервер + клиент): $(9.84 + 6.29) / 7.532 = \mathbf{2.141\,\text{CPU-с / Гбит}}$.

## 3. Разбор причин TCP Retransmits, сокетных буферов и локализации потерь

При исходном замере на одиночном потоке (`-P 1`) без тюнинга сокетных буферов наблюдалось 3087 ретрансмитов при 0% потерь на ICMP, тогда как в режиме `-P 4` ретрансмиты отсутствовали (0).

### 3.1 Локализация потерь (где терялись пакеты):
- **Сетевые интерфейсы (`veth`):**
  Счётчики интерфейсов `veth-host` и `veth-client` (`ip -s link show`) показали **0 errors, 0 dropped** (обработано >1 570 000 пакетов). Потерь на уровне виртуальных интерфейсов нет.
- **Сокеты WDTT (`wdtt-server` и `wdttd`):**
  Инспекция через `ss -u -a -m` показала счётчик дропов `d0` (ноль сброшенных пакетов в очередях приёма сокетов WDTT).
- **Сокет релея Coturn (`coturn relay`):**
  Счётчик дропов в `ss -u -a -m` на сокете релея зафиксировал `d176`, что точно коррелирует с метрикой ядра `nstat UdpRcvbufErrors` (378 пакетов с учётом дуплекса).
  *Причина:* Внутренний однопоточный event loop Coturn при пакетной нагрузке свыше 100 000 pps не успевал вычитывать сокет из-за короткого дефолтного буфера приёма ядра.

### 3.2 Поведение ядра при `setsockopt(SO_RCVBUF, 4MB)` и `getsockopt`:
- По умолчанию в Linux: `net.core.rmem_default = 212992` (208 КБ).
- Ядро Linux удваивает значение буфера при вызове `setsockopt` для учёта накладных расходов структур `sk_buff` (`2 * size`).
- При вызове `setsockopt(SO_RCVBUF, 4 * 1024 * 1024)` на настроенном хосте:
  `getsockopt(SO_RCVBUF)` возвращает **8 388 608 байт (8 МБ)**.
- **Однако на машине без root и на Android-клиенте:**
  Параметр ядра `net.core.rmem_max` ограничен (обычно теми же 208–212 КБ). Непривилегированный процесс не может превысить `rmem_max`: ядро **молча зажимает** (clamps) запрошенный размер до системного максимума.

### 3.3 Архитектурное решение проблемы без правки `sysctl` на ПК и Android:
Так как обычный пользователь на десктопе и приложение на Android (minSdk 28) не имеют root-прав для изменения `sysctl net.core.rmem_max`, полагаться на раздувание буферов сокета ядра **нельзя**.

Архитектура решает проблему на уровне прикладного ввода-вывода (Этап 4.1):
1. **Батчинг системных вызовов (`recvmmsg`):**
   Вместо поодиночного чтения `recvfrom` (1 пакет = 1 системный вызов) сокет опустошается пачками по 32–64 дейтаграммы за один вход в ядро. Это снижает частоту переключений контекста на ~90%, ускоряя вычитку сокета в разы.
2. **Zero-Allocation Slab Buffer Pool:**
   Память под пакеты выделяется заранее монолитным блоком. Процесс чтения не блокируется аллокатором кучи (`malloc`), предотвращая задержки вычитки.
3. **Pipelined Workers (Вариант А из ADR 0007):**
   Поток приёма (`RX Worker`) освобождён от тяжелых криптографических операций и ресеквенсинга: его единственная задача — мгновенно забирать дейтаграммы из ядра и складывать указатели в lock-free SPSC очередь. В результате буфер ядра 208 КБ никогда не переполняется даже при пиковых всплесках TCP CWND.
