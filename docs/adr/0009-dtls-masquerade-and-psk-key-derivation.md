# ADR 0009: DTLS-маскировка канала и деривация ключей из PSK (`docs/adr/0009`)

- **Статус:** Принято (запланировано к реализации)
- **Дата:** 2026-11-18
- **Авторы:** Senior Rust Network Engineer
- **Лицензия:** GPL-3.0 (независимая реализация по спецификации `docs/PROTOCOL.md`)

---

## 1. Контекст

`docs/PROTOCOL.md:43` в диаграмме стека называет слой «Шифрование DTLS 1.2 / 1.3
Record», а `:102` подразумевает существование «DTLS CID» в таблице авторизованных
сессий. Фактически **DTLS в проекте не реализован нигде**: слой объявлен в
спецификации, но не имеет ни кода, ни зависимостей, ни описания хендшейка,
ни длин CID, ни набора cipher suite.

Сегодня рабочий транспорт — TURN over TCP/TLS с ChannelData-фреймингом; WDTT-кадры
идут как есть внутри ChannelData. Внешне поток выглядит как TLS-сессия к
видеосерверу, но полезная нагрузка внутри ChannelData не замаскирована.

Требуется довести проект до состояния, в котором поток неотличим от настоящего
медиасеанса WebRTC, включая слой DTLS-записей.

### 1.1 Жёсткое ограничение транспорта

На TCP/TLS-потоке TURN первый байт каждого юнита обязан быть `0x00..0x3F` (STUN)
или `0x40..0x7F` (ChannelData), иначе `decode_tcp_frame` возвращает ошибку
(`crates/turn/src/transport.rs:106-111`). Настоящая DTLS-запись имеет content type
`0x14`–`0x17`, то есть **не может** идти по этому потоку напрямую.

Следствие: DTLS-записи обязаны находиться **внутри** ChannelData-payload. DTLS —
это вложенный слой маскировки, а не замена транспорта. Это согласуется с
исходным замыслом `PROTOCOL.md`, где DTLS стоит в стеке над TURN.

### 1.2 Требования к маскировке

- Поток должен быть неотличим от обычного медиатрафика WebRTC для пассивного
  DPI: корректный DTLS 1.2 хендшейк, `application_data`-записи с правдоподобным
  темпом и размерами.
- Устойчивость к активному зондированию: посторонний «зонд» не должен
  получить ответ, отличный от молчания (это уже обеспечивает Pre-Auth Knock,
  см. §1.3).
- Минимум новой криптографической поверхности: не заводить PKI, не вводить
  сертификаты, не расширять секретный материал.

---

## 2. Решение

### 2.1 Версия DTLS: 1.2

Принимается **DTLS 1.2** (не 1.3) по трём причинам:

1. **Профиль трафика.** Реальные WebRTC-стеки (Chrome, pion, libwebrtc) в
   подавляющем большинстве сессий используют DTLS 1.2. DTLS 1.3 встречается
   редко и сам по себе является аномалией на фоне обычного медиапотока.
2. **Опасность ТСПУ.** Требование пользователя: ТСПУ может блокировать
   TLS 1.3. DTLS 1.3 семантически ближе к 1.3 и разделяет часть его
   отпечатков; 1.2 — более консервативный и «обычный» выбор.
3. **Зрелость.** Существующие реализации (pion/dtls, `webrtc-dtls`) зрелее
   именно в 1.2; набор расширений и формат записей стабильнее.

### 2.2 Ключевой материал: деривация из PSK

**Отвергается** вариант с настоящим self-signed сертификатом и проверкой
отпечатка. Причины:

- Сертификат — это новый секрет, который нужно хранить, передавать и
  проверять; это расширяет поверхность атаки.
- Аутентификация между клиентом и сервером **уже решена** слоем Pre-Auth
  Knock (`crates/crypto/src/knock.rs`): PSK + ChaCha20-Poly1305 + HKDF-SHA256,
  с молчаливым отбросом неавторизованных зондов.
- Сертификат нужен только для того, чтобы DPI видел «настоящую» цепочку
  доверия. Но DPI не может проверить цепочку к self-signed сертификату
  сколько-нибудь осмысленно — он видит лишь факт наличия валидной с точки
  зрения протокола структуры. Тот же эффект достигается синтетическим
  хендшейком.

**Принимается:** весь ключевой материал DTLS выводится из PSK.

```
PSK
 └─ HKDF-SHA256(salt = b"WDTT-DTLS-v1", info = b"dtls/key-material")
     ├─ client_write_key (16 B)  AES-128-GCM
     ├─ server_write_key (16 B)  AES-128-GCM
     ├─ client_write_iv  ( 4 B)  → 8 B nonce = epoch || seq
     ├─ server_write_iv  ( 4 B)
     └─ cid              ( 8 B)  произвольный, выводится из PSK и session id
```

Это переиспользует существующий KDF-слой (`crates/crypto`) и не добавляет
новых секретов.

### 2.3 Структура DTLS-записи

Записи строятся по формату RFC 6347 (DTLS 1.2):

```
ContentType (1 B) | Version (2 B, 0xFEFD) | Epoch (2 B) |
Sequence (6 B)    | Length (2 B)          | Payload
```

- `ContentType`: `0x16` Handshake при хендшейке, `0x17` ApplicationData в
  устойчивом состоянии.
- `Version` = `0xFEFD` (DTLS 1.2).
- Epoch начинается с 0 (хендшейк) и переходит в 1 после завершения
  (устойчивое состояние), как в настоящем DTLS.
- Хендшейк: один `ClientHello` (с `use_srtp`, `extended_master_secret`,
  `renegotiation_info` и прочими расширениями, характерными для WebRTC),
  затем `ServerHello`, `Certificate` (синтетический, самоподписанный,
  сгенерированный детерминированно из PSK), `ServerKeyExchange`,
  `ServerHelloDone`, `ClientKeyExchange`, `ChangeCipherSpec`, `Finished`.
- Устойчивое состояние: `ApplicationData`-записи, содержащие WDTT-кадр целиком.
- CID: 8 байт, передаётся в расширении `connection_id` (RFC 9146). На TCP он
  избыточен для маршрутизации, но именно его наличие делает поток похожим
  на WebRTC.

### 2.4 Точка врезки

Трансформ врезается в **три парных места**: отправка и приём на клиенте, плюс
симметричные места на сервере. Разведка (см. отчёт по коду) нашла пять
независимых производителей `FrameType::Data`; все они должны быть покрыты,
иначе провод станет асимметричным:

| Позиция | Файл:строка | Роль |
| :--- | :--- | :--- |
| клиентский TUN | `crates/core/src/tunnel.rs:1478` | основной путь |
| UDP-режим | `crates/core/src/tunnel.rs:805` | альтернативный транспорт |
| non-TUN stream | `crates/core/src/tunnel.rs:1143` | прокси-режим |
| сервер UDP | `crates/core/src/tunnel.rs:1895` | приёмная сторона |
| сервер TCP/TLS | `crates/core/src/tunnel.rs:2368` | приёмная сторона |

Плюс обратные (принимающие) места: клиент `:1487-1512`, сервер UDP `:1802-1810`,
сервер stream `:2281-2294`; а также knock-кадры `:1647-1666` и ответ `:2530`.

Трансформ реализуется **один раз** в отдельном модуле (см. §4) и вызывается
из всех перечисленных точек. Это исключает асимметрию провода.

### 2.5 Что не меняется

- Слой TURN/ChannelData остаётся как есть: DTLS-запись целиком лежит внутри
  ChannelData-payload.
- Knock-слой остаётся как есть и продолжает обеспечивать аутентификацию.
- Формат WDTT-кадра (`crates/proto/src/frame.rs`) не меняется: DTLS оборачивает
  уже готовый кадр.
- `TunnelMode` в `crates/proto/src/url.rs` обретает смысл: `Dtls` включает
  новый слой, `DirectRtp` — нет. Сейчас `TunnelMode` не читается вне `url.rs`,
  так что совместимость URL не ломается.

## 3. Последствия

### Положительные

- Поток становится неотличимым от медиасеанса WebRTC на уровне формата записей.
- Нет новой PKI-поверхности: всё выводится из уже существующего PSK.
- Переиспользуется существующий транспорт и knock-слой.
- Наконец реализуется слой, объявленный в `PROTOCOL.md` с самого начала.

### Отрицательные и риски

- **Криптографический код — новая поверхность.** Даже при деривации из PSK
  появляется код обработки записей, счётчиков, epoch-переходов. Митигация:
  минимизировать объём (только 1.2, только AES-128-GCM, без renegotiation),
  покрыть тестами, изолировать в одном модуле.
- **Ложная безопасность.** Маскировка не является шифрованием содержимого:
  скрытность обеспечивает транспорт (TLS), а DTLS-слой даёт только
  правдоподобие формата. Это надо явно отразить в `THREAT_MODEL.md`.
- **Усложнение отладки.** Асимметрия провода (если какая-то точка врезки
  забыта) даст тонкие потери трафика. Митигация: единая точка вызова,
  тест на полноту покрытия.
- **Стоимость CPU.** Дополнительный слой AEAD на каждый пакет. Ожидается
  прирост `%usr` порядка единиц процентов; замер обязателен.

## 4. План реализации

1. **Модуль `crates/crypto/src/dtls.rs`** (или отдельный крейт `wdtt-dtls`):
   типы `Record`, `ContentType`, `Epoch`, `SequenceNumber`; функции
   `key_schedule(psk) -> DtlsKeys`, `seal(keys, epoch, seq, plaintext) -> Record`,
   `open(keys, record) -> plaintext`; синтез `ClientHello`/`ServerHello`/
   `Certificate` с корректными расширениями.
2. **Интеграция в `tunnel.rs`**: обёртка `DtlsChannel` вокруг пары
   (отправка кадра, приём кадра), применяемая во всех пяти точках отправки
   и трёх точках приёма.
3. **Флаг режима**: чтение `TunnelMode` из URL; `DirectRtp` — прежнее поведение
   (для отката).
4. **Тесты**: roundtrip записи, деривация ключей детерминирована, `!=` версия,
   `!=` content type; интеграционный тест «полный хендшейк + обмен данными».
5. **Документация**: обновить `PROTOCOL.md` §2 (спецификация DTLS-слоя),
   зафиксировать выбор 1.2 и PSK-деривацию; дополнить `THREAT_MODEL.md`
   оговоркой, что маскировка не заменяет шифрование.
6. **Проверка в netns**: полный цикл с DTLS-слоем, замер пропускной
   способности относительно текущего, проверка, что поток не ломается
   при смене epoch.
