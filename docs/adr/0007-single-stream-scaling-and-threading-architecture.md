## 1. Контекст и проблема производительности (Profiling Data)

В ходе профилирования на Этапе 3.5 / 4.1 ([docs/flamegraph_stage4_1.svg](file:///home/keyl/Projects/WDTT-fork/docs/flamegraph_stage4_1.svg)) на одиночном TCP-потоке со скоростью **1140.78 Мбит/с** (~1.14 Гбит/с) получены следующие эмпирические показатели (`pidstat -t` и `mpstat -P ALL`):

```
PID       TID    %usr   %system  %wait    %CPU   Command
229476      -   15,36     84,52   0,00   99,88   wdtt-server
```

### Ключевые выводы профилирования:
1. **Однопоточный движок упёрся в 100% одного ядра:**
   Суммарная загрузка процессора сервером составляет **99.88% одного ядра**.
2. **Доминирование системных вызовов (%system = 84.52%):**
   - 84.5% процессорного времени тратится внутри ядра на системные вызовы `recvfrom` и `sendto`, переключение контекста userspace $\leftrightarrow$ kernel и копирование сокетных буферов `sk_buff`.
   - Пользовательский код Rust (%usr = 15.36%) тратит ресурсы на декодирование фреймов WDTT, инспекцию WireGuard-заголовков и поиск в ресеквенсере.
3. **Ограничение сокетных буферов на клиентах и Android:**
   Увеличение `SO_RCVBUF` до 4 МБ через `setsockopt` эффективно на машинах с настроенным `sysctl net.core.rmem_max`, однако на смартфонах Android и у обычных пользователей без root `rmem_max` ограничен 208 КБ. Попытка выставить 4 МБ там принудительно зажимается ядром до 208 КБ, что при пиковых всплесках трафика (TCP burst) приведёт к отбрасыванию пакетов в сокете.

## 2. Программа оптимизации Этапа 4.1 (В рамках одного потока)

Перед изменением многопоточной архитектуры проводятся микрооптимизации одного потока с замерами «до» и «после»:

1. **Zero-Allocation Packet Slabs (Пулы буферов):**
   - Устранение `BytesMut::new()` и `Bytes::copy_from_slice()` на горячем пути.
   - Использование предвыделенного пула буферов (slab allocator) на 512 фреймов с повторным использованием памяти.
2. **Батчинг системных вызовов (`recvmmsg` / `sendmmsg`):**
   - Приём и отправка пачками до 32–64 дейтаграмм за один системный вызов.
   - Снижение количества переключений контекста со 130 000 до ~4 000 syscalls/сек (сокращение накладных расходов ядра на ~70%).
3. **UDP GSO / GRO (`UDP_SEGMENT`, `UDP_GRO`):**
   - Использование Generic Receive/Segmentation Offload ядра для передачи агрегированных супер-пакетов WireGuard.

## 3. Варианты многопоточной архитектуры (Scaling beyond 1 core)

Если после оптимизаций Шага 4.1 одиночный поток продолжает упираться в ядро (>85% CPU на скоростях >1.5 Гбит/с), предлагаются два архитектурных решения:

```
ВАРИАНТ А: Pipelined Workers (Actor/Ring Pipeline)
┌──────────────┐   lock-free ring    ┌──────────────────────┐   lock-free ring    ┌──────────────┐
│  RX Worker   │ ──────────────────> │ Framing/Resequencer  │ ──────────────────> │  TX Worker   │
│  (recvmmsg)  │   (zero-copy)       │ Worker Pool (1-2 CPU)│   (zero-copy)       │  (sendmmsg)  │
└──────────────┘                     └──────────────────────┘                     └──────────────┘
  Core 1 (sys)                                Core 2 (usr)                          Core 3 (sys)

ВАРИАНТ Б: Thread-per-Core (Shared-Nothing с BPF Steering)
┌─────────────────────────────────┐       ┌─────────────────────────────────┐
│ Worker 1 (Core 1): RX+Decap+TX  │       │ Worker 2 (Core 2): RX+Decap+TX  │
│ SO_REUSEPORT (Flow Hash BPF)    │       │ SO_REUSEPORT (Flow Hash BPF)    │
└─────────────────────────────────┘       └─────────────────────────────────┘
```

### Сравнение вариантов:

| Критерий | Вариант А (Pipelined Workers) | Вариант Б (Thread-per-Core) |
| :--- | :--- | :--- |
| **Принцип работы** | Разделение стадий: приём сокета $\to$ обработка $\to$ отправка в WG | Независимые изоляты с BPF-хэшированием потоков по 5-tuple |
| **Утилизация CPU** | Системные вызовы `recv`/`send` вынесены на отдельные ядра | Каждое ядро полностью обслуживает свою долю сетевых потоков |
| **Сложность синхронизации**| Требуются lock-free SPSC очереди (crossbeam/rtrb) | Shared-nothing: нулевые блокировки между потоками |
| **Поддержка ресеквенсера** | Единое состояние ресеквенсера на поток | Ресеквенсер локален для каждого ядра (по 5-tuple) |
| **Применимость к мобильным ОС** | Высокая (работает на Android без root и без SO_REUSEPORT) | Ограниченная (требует BPF SO_REUSEPORT в ядре) |

---

## 4. Решение и план реализации

1. **Приоритет 1 (Этап 4.1):** Реализовать zero-allocation буферные пулы и батчинг сокетов в `crates/core` и `crates/turn`. Замерить прирост пропускной способности и снижение `%system` CPU.
2. **Приоритет 2 (Этап 4.2):** Для Android и десктопа принять **Вариант А (Pipelined Workers)**, так как он не требует привилегий ядра и гарантирует перенос затрат на ввод-вывод с вычислительного потока. Для многопоточного режима (Этап 4.2) мультиплексирование потоков TURN распределяется по схеме Hybrid Spray (ADR 0006).
