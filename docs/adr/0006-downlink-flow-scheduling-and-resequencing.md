# ADR 0006: Downlink Flow-Scheduling, Anti-Replay Skew Management и Silent Discard

## Статус
Принято (Дополнение к Gate 0)

## Контекст
При проектировании протокола WDTT v2 и архитектуры ядра выявлены четыре взаимосвязанных критических вопроса:

1. **Downlink Flow-Scheduling при использовании Kernel WireGuard:**
   На направлении Uplink (клиент $\to$ сервер) клиент в userspace видит исходные IP-пакеты до шифрования WireGuard и может легко вычислять Flow-Hash (5-tuple).
   На направлении Downlink (сервер $\to$ клиент) сервер с **Kernel WireGuard** получает от ядра уже зашифрованные WireGuard Data пакеты (`Type = 4`). Их полезная нагрузка зашифрована сессионным ключом WireGuard, поэтому серверный прокси **не видит 5-tuple внутреннего IP-пакета**.
2. **Anti-replay окно WireGuard (8128) при высоких скоростях:**
   При пропускной способности 1 Гбит/с частота передачи пакетов составляет $\sim 104{,}000$ pps (при среднем MTU 1200 байт). Если разница сетевых задержек (skew) между двумя параллельными потоками составляет 100 мс, расхождение счетчиков пакетов достигает:
   $$\Delta C = 104{,}000 \times 0.1 = 10{,}400 \text{ пакетов}$$
   Это превышает размер скользящего anti-replay окна WireGuard (8128 пакетов, RFC 6479). Пакеты с более медленного потока будут **молча отброшены ядром WireGuard на приёме (silent drop)**.
3. **Производительность одного большого TCP-потока:**
   При строгом Flow-Hashing один TCP-поток всегда привязан к одному физическому DTLS/TURN-потоку. Если пропускная способность одного TURN-потока ограничена (например, 50–100 Мбит/с на релее VK), то один TCP-поток не сможет утилизировать суммарную полосу 8 потоков.
4. **Реализация Silent Discard в присутствии DTLS 1.2:**
   Стандартный сервер DTLS 1.2 при получении `ClientHello` от сканера обязан ответить `HelloVerifyRequest` или `ServerHello`, что демаскирует сервер перед сетевыми зондировщиками (Censys, Shodan, ТСПУ).

---

## Решение

### 1. Схема Downlink при Kernel WireGuard vs Userspace WireGuard

Принята двухуровневая модель:

#### Вариант (А) — Сервер с Kernel WireGuard + Клиентский Ресеквенсер по счетчику WG
- **Наблюдение:** В заголовке WireGuard Data Packet (`Type = 4`, RFC 8439) первые 16 байт передаются в открытом виде:
  - Байты 0..3: `Type = 0x04`
  - Байты 4..7: `Receiver Index` (32 бита)
  - Байты 8..15: `Counter` (64 бита, монотонно возрастает на 1 для каждого переданного пакета в рамках сессии).
- **Механизм сервера:** Сервер распределяет исходящие от Kernel WG пакеты по активным здоровым потокам с балансировкой (Deficit Round Robin / емкость потока).
- **Механизм клиента (WG-Counter Resequencer):**
  - До передачи пакета в локальный сокет WireGuard клиент считывает 64-битный `Counter` из открытого заголовка.
  - Пакеты помещаются в неблокирующий кольцевой буфер упорядочивания (`ResequencerRing`, емкость 2048–4096 слотов).
  - Пакеты выдаются в WireGuard в строгом порядке возрастания счетчика.
  - Таймаут удержания пакета: 3–5 мс. Если пакет физически потерян в сети, окно сдвигается, отдавая обработку потерь протоколу TCP.

#### Вариант (Б) — Сервер с Userspace WireGuard (`boringtun`)
- Сервер видит внутренний 5-tuple до шифрования WireGuard и выполняет симметричный Flow-Hashing.
- Доступен как feature flag `userspace-wg` для серверов без модуля ядра Linux.

### 2. Защита от сбоев Anti-Replay окна (Skew Limiter + tc netem test)

Для исключения silent drops при расхождении задержек потоков до 100 мс реализуется **трехконтурная защита**:

1. **Active Skew Limiter в планировщике:**
   - Каждый поток непрерывно измеряет сглаженный RTT ($SRTT$) через `PING`/`PONG` кадры (каждые 500 мс).
   - Максимально допустимый джиттер между самым быстрым и самым медленным активным потоком ограничивается порогом:
     $$\Delta RTT_{\text{max}} = 35 \text{ мс}$$
     (При 104k pps задержка 35 мс соответствует расхождению $\sim 3640$ пакетов, что гарантированно укладывается в окно 8128 с двукратным запасом).
   - Если задержка потока превышает $\Delta RTT_{\text{max}}$, планировщик временно прекращает направлять в него новые пакеты до выравнивания очереди.
   - Если задержка потока превышает 75 мс дольше 2 секунд — поток переводится в статус `DEGRADED`, временно исключается из балансировки и переподключается в фоне.
2. **Клиентский Ресеквенсер:** Буферизирует до 2048 пакетов, сглаживая микро-джиттер до 20 мс без нагрузки на CPU.
3. **Автоматизированный тест с `tc netem` (`tests/netem_replay_skew.sh`):**
   - На тестовом стенде эмулируются два канала: Path 1 с задержкой 10 мс, Path 2 с задержкой 110 мс (дельта 100 мс).
   - Генерируется трафик `iperf3` со скоростью 1 Гбит/с.
   - Критерий успешности теста: **0 отброшенных пакетов по счетчику anti-replay WireGuard** (`wg show <iface> dump` / метрики boringtun).

### 3. Производительность одного TCP-потока: Гибридный планировщик (`hybrid-spray`)

- **Проблема:** Строгий Flow-Hash ограничивает скорость одного TCP-соединения скоростью одного TURN-потока.
- **Решение:**
  - **Режим Multi-Flow:** При наличии множества потоков в системе (типовой веб-серфинг, торренты, несколько приложений) работает классический Flow-Hash — zero latency, нулевая буферизация.
  - **Режим Single-Flow Spray (автоматический):** Если планировщик фиксирует, что один TCP-поток утилизирует $> 80\%$ емкости одного TURN-потока, а остальные потоки простаивают, активируется распыление пакетов (Packet Spraying) по всем здоровым потокам с гарантированным упорядочиванием через клиентский WG-Counter Resequencer.
  - Это позволяет одному потоку TCP разгоняться до суммарной скорости всех TURN-каналов.

### 4. Реализация Silent Discard при наличии DTLS

- Для обеспечения полной невидимости сервера применен **Outer Auth/Obfs Envelope** (внешний конверт аутентификации):
  - Любой UDP-пакет, приходящий на внешний порт сервера (включая начальный `ClientHello`), обязан быть обёрнут в криптографический контейнер RTP-obfs (AEAD ChaCha20-Poly1305 / AES-GCM), ключ которого выведен из предварительно разделяемого секрета (PSK / пароль сервера).
  - При получении датаграммы сервер первым делом выполняет валидацию тега аутентификации AEAD.
  - **Если тег не совпадает (случайный зонд, сетевой сканер Shodan, попытка подключения без пароля):**
    - Сервер **немедленно сбрасывает пакет без ответа**.
    - Никаких `HelloVerifyRequest`, `ServerHello`, ICMP Unreachable или сбросов соединения наружу не отправляется.
  - Только после успешной проверки подлинности внутреннего содержимого пакет передается в DTLS-машину состояний или сетевой драйвер.
- Для внешнего наблюдателя порт сервера выглядит как полностью немаршрутизируемый «черная дыра» (Blackhole).

### 5. Ограничения VK TURN по числу аллокаций

- В ходе анализа исходного кода `qwdtt` и спецификации STUN/TURN (RFC 5766 Section 6.2) установлено:
  Серверы VK coturn возвращают **STUN Error 486 (Allocation Quota Reached)** при попытке создать слишком много одновременных аллокаций на один аккаунт/учетные данные звонка, либо при слишком частых всплесках запросов Allocate.
- **Архитектурные ограничения в `wdtt-rs`:**
  - Верхняя граница пула потоков на один VK-хеш жестко ограничена:
    $$N_{\text{max}} = 8 \text{ потоков на один хеш}$$
  - Старт потоков выполняется со ступенчатым интервалом (staggering) не менее 250 мс между вызовами `Allocate`.
  - Расширение пула до 16 потоков допускается **только при наличии 2 и более независимых хешей VK звонков**.
