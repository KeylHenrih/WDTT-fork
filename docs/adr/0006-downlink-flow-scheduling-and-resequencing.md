# ADR 0006: Downlink/Uplink Resequencing, Skew Control, Crypto-Envelope и Scheduler Strategies

## Статус
Принято (Утверждено с правками к Gate 0)

## Контекст
В ходе ревью решений по datapath и протоколу v2 согласованы 9 ключевых уточнений:
1. **Расчёт размера ресеквенсера и поведение при переполнении:**
   При пропускной способности 1 Гбит/с ($\sim 104{,}000$ pps при среднем размере пакета 1200 байт) и задержке расхождения потоков $\Delta t_{\text{skew}} = 100$ мс расхождение пакетов составляет:
   $$S = \lceil 104{,}000 \times 0.100 \rceil = 10{,}400 \text{ пакетов}$$
   При ограничении джиттера планировщиком до $\Delta t_{\text{skew}} \le 35$ мс:
   $$S = \lceil 104{,}000 \times 0.035 \rceil = 3{,}640 \text{ пакетов}$$
2. **Сессии WireGuard и Receiver Index:**
   Согласно спецификации WireGuard (Jason A. Donenfeld, *WireGuard: Next Generation Kernel Network Tunnel*, Раздел 5.4), пакеты данных (`Type = 4`) несут 4-байтный `Receiver Index` и 64-битный `Counter`. При рекеинге (каждые 120 с) активны две пары ключей одновременно с независимыми счетчиками от 0. Пакеты Handshake (`Type 1` Initiation, `Type 2` Response, `Type 3` Cookie) не имеют 64-битного счетчика данных.
3. **Uplink при Packet Spraying:**
   При распылении пакетов клиентом на передачу аналогичный разброс счетчиков возникает на сервере перед отправкой в порт WireGuard.
4. **Обратная связь по реордерингу (Reordering Feedback):**
   Вместо только периодических RTT Ping/Pong, приёмник непосредственно наблюдает глубину перестановок $\Delta C = C_{\text{highest}} - C_{\text{expected}}$ и сообщает её отправителю.
5. **Проблема тройного шифрования (Triple Crypto Tax):**
   Применение внешнего AEAD-конверта на *каждый* пакет вместе с DTLS и WireGuard даёт избыточный оверхед по CPU (на 30–40% больше тактов на байт) и съедает 24–28 байт MTU на служебные заголовки.
6. **Маскировка под RTP внутри DTLS:**
   Внутри DTLS полезная нагрузка полностью зашифрована (`ContentType = 23 ApplicationData`). Заголовок RTP внутри DTLS невидим для DPI и лишь расходует 12 байт MTU.
7. **Квоты аллокаций VK Calls:**
   Число одновременных аллокаций $N_{\text{max}} = 8$ является предварительной оценкой по исходному коду `qwdtt` (где зафиксирована ошибка `STUN 486 Allocation Quota Reached`) и подлежит точному измерению на внешнем тестовом стенде.
8. **Корректные ссылки на спецификации:**
   Формат пакетов WireGuard регламентируется спецификацией WireGuard (Jason A. Donenfeld), а не RFC 8439 (который определяет алгоритм ChaCha20-Poly1305).
9. **Стратегии планировщика как переключаемые гипотезы:**
   До проведения сквозных замеров на Этапе 4 алгоритмы планировщика оформляются как переключаемые флаги: `flow-hash`, `hybrid-spray` и `direct` (без ресеквенсера).

---

## Решение

### 1. Расчёт буфера ресеквенсера и поведение при переполнении

Размер кольцевого буфера ресеквенсера вычисляется из формулы:
$$S_{\text{capacity}} = 2^{\lceil \log_2(\text{PPS}_{\text{max}} \times \Delta t_{\text{skew\_max}}) \rceil}$$
- Для максимального проектного режима (100 мс skew, 104k pps): емкость составляет $16{,}384$ слота ($2^{14}$).
- Для нормального режима со Skew Limiter ($\le 35$ мс skew): емкость составляет $4{,}096$ слотов ($2^{12}$).

#### Поведение при переполнении (Overflow & Gap Skip Policy):
Если приходит пакет со счетчиком $C_{\text{new}}$, опережающим ожидаемый $C_{\text{expected}}$ на величину, превышающую емкость буфера ($C_{\text{new}} - C_{\text{expected}} \ge S_{\text{capacity}}$), либо истекает таймаут ожидания потерянного пакета (таймаут «дыры» $\tau_{\text{gap}} = 3..5$ мс):
1. Ресеквенсер **не блокирует поток и не отбрасывает новые пакеты**.
2. Выполняется принудительный сдвиг окна (Fast-Forward): все непрерывные пакеты до первой дыры выдаются в WireGuard.
3. Пропущенные пакеты («дыра») объявляются утраченными в сети: $C_{\text{expected}}$ перескакивает через пропуск.
4. Пакет $C_{\text{new}}$ успешно размещается в буфере.
5. Запрос повторной передачи возлагается на вышележащий протокол (TCP/QUIC).

---

### 2. Мультиплексирование по Receiver Index и Handshake Bypass

1. **Изоляция по Receiver Index:**
   Ресеквенсер хранит независимые контексты упорядочивания (`expected_counter`, кольцевой буфер слотов, таймер дыры) в структуре `HashMap<u32, ReceiverSessionState>`:
   - Ключ: 4-байтный `Receiver Index` из заголовка Type 4 WireGuard.
   - Это гарантирует корректную работу при ротации ключей WireGuard (rekeying), когда одновременно активны старая и новая пары ключей.
   - Сессии с неактивным Receiver Index очищаются по таймауту (180 секунд).
2. **Handshake Bypass (Пакеты типов 1–3):**
   При получении пакетов типов 1 (Initiation), 2 (Response) и 3 (Cookie Reply):
   - Пакет **не помещается в ресеквенсер** и не участвует в проверке счетчика.
   - Пакет немедленно пересылается напрямую в сокет WireGuard, обеспечивая минимальную задержку согласования ключей.

---

### 3. Симметричный ресеквенсер на Uplink (Сервер)

В режиме `hybrid-spray` клиент распыляет пакеты по разным потокам на Uplink.
- Сервер перед передачей UDP-пакетов в локальный сокет WireGuard (`127.0.0.1:<wg_port>`) пропускает их через аналогичный **Server WG-Counter Resequencer**.
- Таким образом, ядро Linux WireGuard и на клиенте, и на сервере получает строго упорядоченный поток пакетов без нарушения anti-replay окна.

---

### 4. Skew Limiter с обратной связью по измеренному реордерингу

В дополнение к контрольным RTT-замерам Ping/Pong:
1. Приёмный ресеквенсер непрерывно рассчитывает мгновенную глубину перестановок:
   $$\text{ReorderDepth} = C_{\text{highest\_received}} - C_{\text{expected}}$$
2. Значение $\text{ReorderDepth}$ и дельта времени прибытия упаковываются в контрольные кадры `STREAM_FEEDBACK` (отправляются каждые 100 мс или при скачке $\text{ReorderDepth} > 1000$).
3. Отправитель при получении `STREAM_FEEDBACK`:
   - Если $\text{ReorderDepth} > 0.5 \times S_{\text{capacity}}$, снижает вес отстающего потока в балансировщике.
   - Если $\text{ReorderDepth} > 0.75 \times S_{\text{capacity}}$, временно замораживает отправку новых пакетов в отстающий поток до выравнивания очереди.

---

### 5. Оптимизация внешнего конверта: Handshake-Only Pre-Auth Knock

Во избежание тройного шифрования (WireGuard + DTLS + Outer AEAD) на горячем пути:
1. **Фаза Knock (Handshake):**
   Внешний Pre-Auth Knock обязателен **только для первого пакета сессии** (`ClientHello` / `HANDSHAKE_INIT`).
   - **Маскировка и отсутствие открытых сигнатур:**
     Пакет Knock вне DTLS не содержит открытых текстовых меток или магических констант. Полезная нагрузка шифруется ChaCha20-Poly1305 с использованием `knock_key` (выведенного из PSK через HKDF):
     `[Nonce: 12B | Ciphertext(timestamp, client_nonce, session_id): 40B | Poly1305 Tag: 16B | Random Padding: 16..128B]`.
     Для DPI и внешних пробок пакет выглядит как высокоэнтропийный шум переменного размера (84..196 байт), неотличимый от медиатрафика звонка.
   - **Защита от Replay (Nonce Cache):**
     Сервер ведет ограниченный кольцевой кеш использованных `client_nonce` с очисткой по TTL (`now ± max_skew_sec`, по умолчанию 60 секунд). Повторный пакет с тем же нонсом немедленно отбрасывается.
   - **Silent Discard:**
     Если пакет не расшифровывается ключом `knock_key` или содержит устаревший timestamp $\implies$ сервер сбрасывает его молча (**0 байт ответа**).

2. **Фаза Steady-State Data (Привязка авторизации и миграция):**
   - **Привязка:** После успешной проверки Knock сервер привязывает авторизацию к 3-tuple `(Relay IP, Relay Port, session_id)` с временем жизни `session_ttl` (по умолчанию 300 секунд).
   - **Продление:** Каждый входящий аутентифицированный пакет WireGuard / DTLS с этого 3-tuple сдвигает таймер жизни вперёд.
   - **Переиспользование порта (Port Re-use / NAT rebinding):**
     - Если NAT клиента или релея сменил внешний порт (миграция пути) $\implies$ клиент посылает новый замаскированный Knock со своего нового адреса, сервер верифицирует его и безопасно перепривязывает `session_id` к новому 3-tuple.
     - Если освободившийся старый порт переиспользован посторонним источником, трафик от него не пройдёт дешифрование DTLS/WireGuard и будет молча отброшен без продления аренды.
   - **Стоимость по CPU в steady-state:** **0 дополнительных крипто-операций на пакет данных**.
   - **Оверхед по MTU в steady-state:** **0 дополнительных байт** в установившемся режиме.

### 5.1. Безопасность Resequencer: Ограничение скачков и фильтрация

1. **Гарантия аутентификации пакетов перед ресеквенсером:**
   До вызова `resequencer.push()` и функции `advance_to()` доходят **исключительно криптографически аутентифицированные пакеты**:
   - На сервере: пакеты от авторизованного по Knock 3-tuple, прошедшие валидацию DTLS / WireGuard Type 4.
   - На клиенте: пакеты из аутентифицированного TURN ChannelData / DTLS соединения.
   Любой неаутентифицированный мусор отбрасывается на сетевом ingress-уровне и до ресеквенсера не доходит.
2. **Ограничение допустимого скачка счётчика (`MAX_FORWARD_COUNTER_JUMP`):**
   - Максимальный скачок ограничен величиной $65\,536$ пакетов.
   - При обнаружении $\Delta = c - \text{expected} > 65\,536$ (аномальный счётчик или повреждение) пакет отклоняется со сбросом, предотвращая недопустимый скачок `expected_counter` и разрушение окна сессии.
3. **Адаптивный таймаут ожидания дыры (`gap_timeout`):**
   - $\text{gap\_timeout} = \text{clamp}(1.25 \times \text{measured\_skew} + 5\text{ мс}, 5\text{ мс}, 80\text{ мс})$.
   - При межпотоковом skew 35 мс таймаут составляет $\approx 48$ мс, предотвращая ложное объявление пакетов медленного потока потерянными.

---

### 6. Устранение избыточного RTP внутри DTLS

1. **Режим DTLS (по умолчанию):**
   - Внутри DTLS используется компактный 8-байтный заголовок кадра WDTT v2 (`[Magic: 1B][Type: 1B][StreamID: 1B][Flags: 1B][Seq: 2B][Len: 2B]`).
   - Заголовок RTP v2 **не используется** внутри DTLS, так как полезная нагрузка DTLS не видна DPI. Это экономит 12 байт MTU на каждый пакет.
2. **Режим Direct UDP (`-notls`):**
   - Заголовок RTP v2 (12 байт) используется обязательно, формируя профиль медиа-пакета Opus (PT=111) или Video (PT=96) для маскировки перед DPI.

---

### 7. Квоты VK Calls как экспериментальная оценка

- Значение $N_{\text{max}} = 8$ зафиксировано как **архитектурная гипотеза**.
- На внешнем тестовом сервере в рамках запланированных замеров будет проведено точное измерение порога срабатывания `STUN 486 (Allocation Quota Reached)` при параллельных аллокациях с одного хеша.

---

### 8. Конфигурируемые стратегии планировщика (Runtime Pluggable)

В `crates/core` планировщик реализуется через типаж с поддержкой трех переключаемых стратегий:
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum SchedulerStrategy {
    /// Чистый Flow-Hash по 5-tuple (без буферизации, минимальная задержка).
    FlowHash,
    /// Гибридный режим: Flow-Hash для множества потоков, Packet Spraying + Resequencer для одиночного большого потока.
    HybridSpray,
    /// Прямой режим (Round-Robin без ресеквенсера) для замеров базовой деградации.
    DirectRoundRobin,
}
```
Финальный выбор дефолтной стратегии утверждается по измерениям на Этапе 4.
