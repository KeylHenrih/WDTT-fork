# ADR 0002: Спецификация протокола WDTT v2 и многопоточный Flow Hashing

## Статус
Принято (Предложено на Этапе 0)

## Контекст
В существующих проектах (`vk-turn-proxy`, `PWDTT`, `qWDTT`) параллелизация передачи пакетов через N потоков (от 10 до 72) реализована через конкурентную вычитку пакетов воркерами из одного общего буферизированного канала Go (`chan *UDPPacket`).

Следствия такого подхода в baseline:
1. **Катастрофический packet reordering:** Из-за разницы сетевых задержек в параллельных потоках пакеты внутри одного TCP-соединения приходят на сервер вперемешку. Это вызывает каскады Duplicate ACK, резкое уменьшение congestion window и деградацию пропускной способности TCP в 3–5 раз по сравнению с пропускной способностью UDP.
2. **Сбои anti-replay окна WireGuard:** WireGuard имеет жесткое скользящее окно 8128 пакетов. Если запаздывание пакета на отставшем воркере превышает 8128 пакетов по отношению к опережающим воркерам, WireGuard молча отбрасывает его.
3. **Несимметричный возвратный трафик:** На сервере каждый входящий DTLS-поток создавал отдельное UDP-подключение к WireGuard с эфемерного порта, приводя к тому, что WireGuard слал обратные пакеты только в один последний активный поток.

## Рассмотренные варианты
1. **Round-robin распределение пакетов по потокам:**
   - Не решает проблему переупорядочивания TCP, гарантирует джиттер при малейшей асимметрии задержки между потоками.
2. **Flow Hashing (хеширование 5-tuple внутреннего IP-пакета):**
   - Все пакеты одного сетевого потока (src_ip, dst_ip, proto, src_port, dst_port) направляются строго в один и тот же поток.
   - Порядок пакетов в рамках TCP-соединения сохраняется строго FIFO.
   - Разные TCP/UDP потоки параллельно распределяются между N доступными путями, обеспечивая суммарную утилизацию полосы.
3. **Reordering Buffer на стороне сервера/клиента:**
   - Требует буферизации, таймеров и дополнительного копирования памяти, увеличивает задержку (latency) и потребление RAM.

## Решение
1. Принят **Flow Hashing** на базе `SipHash-2-4` от 5-tuple для диспетчеризации пакетов между потоками.
2. Введена спецификация протокола **WDTT v2** (см. `docs/PROTOCOL.md`):
   - 8-байтный заголовок кадра с явной версией (`0xD2`), типом кадра, stream ID, флагами и счетчиком sequence number.
   - Поддержка кадров `DATA`, `HANDSHAKE_INIT/RESP`, `PING/PONG`, `STREAM_FEEDBACK`, `DISCONNECT`.
   - Криптография AEAD (ChaCha20-Poly1305 / AES-128-GCM) с 64-битным монотонным счетчиком в Nonce (без повторов nonce) и скользящей битовой маской anti-replay окна (RFC 6479) без аллокаций.
   - Маскировка трафика под RTP v2 (Opus audio / VP8 video) с рандомизацией длины через padding.
3. Сервер работает в режиме **Silent Discard**: не отвечает на неавторизованные пакеты, предотвращая обнаружение активными зондировщиками.

## Последствия
- Полностью исключены потери пакетов из-за рассинхронизации anti-replay окна WireGuard.
- Пропускная способность одиночного TCP-потока в туннеле возрастает до максимума физической полосы конкретного TURN-пути.
- При отвале отдельного TURN-потока адаптивный контроллер временно переводит его хеши на оставшиеся здоровые потоки и выполняет фоновое переподключение без разрыва всей сессии.
